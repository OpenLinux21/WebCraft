## 概览

这里是整门课程的顶峰。前面各课中，你已经凑齐了前端工艺的完整工具链：用 HTML 搭结构，用 CSS 做表现，用 JavaScript 写行为，用 DOM 实现交互，用 Web Storage 添加记忆。每课都以一个小作品收尾。综合实战不同——它是一个*同时需要所有这些*的作品，并且要像真实应用那样把它们接在一起。

任务书：一块交互式任务看板。添加任务、标记完成、删除任务、看着计数实时更新，然后刷新页面，发现一切都还在。这里没有任何孤立的新知识，要展示的本领是*组合*：一个驱动界面的数据模型，改变模型的事件，从真相重新绘制的渲染步骤，以及搭每一次变更顺风车的持久化。

这一课值得慢下来——它是全课程最长的练习，而它排练的那些习惯（state、render、save），将伴随你此后构建的每一个应用。

## 看板设计：state、render、save

一个决策决定整个构建：**数组就是应用**。可见的一切都派生自一个由普通对象组成的 `tasks` 数组；每次交互修改数组；唯一的 `render()` 从它重绘界面。这就是第 20 课的"状态-渲染"循环，只是这次承载了整个 UI：

```js
// 唯一的真相来源。
let tasks = [
  // { id: 1717, text: "复习第 24 课", done: false }
];

// 唯一的渲染：从 tasks 重建列表 + 计数器。
function render() {
  // 1. 清空列表容器
  // 2. 对每个任务：创建带复选框、文字、删除按钮的 li
  // 3. 更新计数段落
}

// 每次变更都以同样的方式收尾：
function mutate(update) {
  update();
  render();
  save();
}
```

为什么坚持每次从零重建，而不是在现有 DOM 上修修补补？因为它消灭了一整类 bug。屏幕上不可能出现已被删除的任务、漏掉勾选状态的复选框、或者与计数器打架的显示——屏幕*就是*数组，每次都重新盖印。对几十条的列表来说，这点开销毫无感觉，而这份简单胜过一切。

第二个架构决策：**事件委托**。否则每个列表项都得自带两个监听器——而且重建的项还要重新绑定。让列表容器统一监听 `click` 和 `change` 各一次，检查 `event.target`，再分发给对应的变更。新渲染出的项从诞生那一刻起就自动可交互。

```js
list.addEventListener('click', (event) => {
  const li = event.target.closest('li');
  if (!li) return;
  if (event.target.classList.contains('delete')) {
    // 删除 id 为 li.dataset.id 的任务
  }
});
```

## 五步计划

起始代码提供完整的 HTML 和 CSS，外加一个由函数骨架和 TODO 组成的 JavaScript 文件。按顺序推进；每完成一步，应用都保持可运行。

**第 1 步——数据与渲染。** 填写 `render()`：对 `tasks` 中的每个任务，构建一个 `li`，包含复选框（`checked` 取自 `task.done`）、`textContent` 设为任务文字的 `span`，以及删除按钮。设置 `li.dataset.id` 让事件能找到自己的任务。更新 `#done-counter` 的文本。启动时先加载、再调用一次 `render()`。验证：一块空看板配一个合理的计数。

**第 2 步——添加。** 监听表单的 `submit`，`preventDefault()`，取修剪后的输入值，忽略空值，把 `{ id: Date.now(), text, done: false }` 压入 `tasks`。以 `render()` 和 `save()`（save 初期可以是空壳）收尾。清空输入框并让焦点留在里面——小动作，大体验。

**第 3 步——切换与删除。** 按上面的草图，加上委托的 `change` 监听器（复选框）和委托的 `click` 监听器（删除按钮）。每个分支按 id 找到任务，修改数组（删除用 `filter`），并以 `render()` 和 `save()` 收尾。验证：计数器与你的点击严丝合缝。

**第 4 步——持久化。** 现在让 `save()` 成真：`JSON.stringify(tasks)` 写入存储，用 `try/catch` 包裹并配内存回退——正是第 20 课的那对助手。写出带防御式 `JSON.parse` 和结构检查（`Array.isArray`，每项有字符串 `text` 和布尔 `done`）的 `loadTasks()`，任何可疑情况都返回 `[]`。在首次渲染前调用它。验证：在普通标签页里刷新，任务还在；在沙箱预览里刷新，回退路径运行且不报一个错。

**第 5 步——专业收尾。** 给复选框加携带任务文字的 `aria-label`，确保删除按钮有可访问名称，补上第 21 课的 `:focus-visible` 样式，并用一句友好的提示替代空空如也的列表。零任务时刷新：应用看起来是"刻意为之"，而不是"出了故障"。

> **提示：** 别想一口气写完五步。每完成一步就运行一次页面；每个 TODO 的体量都经过设计，保证步与步之间应用始终可用。

## 借自前课的持久化与打磨

这块看板里没有任何东西是本课发明的——这正是重点。save/load 对就是第 20 课那套有防护的模式，换了个键名（`taskboard.v1`）直接请来；可访问性层是第 21 课清单的落地：真正的 `<button>`、关联的 label、可见的键盘焦点；视觉状态则遵循第 22 课的一致性思想：`.done` 类是 render() 切换的唯一样式钩子，其余交给 CSS。

一个值得点名的打磨细节，因为它会出现在每个真实应用里：**焦点管理**。用键盘删除任务后，焦点原本在被移除的按钮上——它消失了，键盘用户被一把甩回页首。一行修复就能让删除后焦点落到合理的位置，比如表单输入框：

```js
// 用键盘删除任务之后：
document.querySelector('#task-input').focus();
```

还有一件事值得花点心思：id。`Date.now()` 在这个规模上够用——单用户、单看板，唯一性足够。将来若要在同一毫秒里创建成千上万条数据，请换 `crypto.randomUUID()`；理解*为什么*需要 id，比选哪一个更重要。

> **试一试：** 看板跑通之后，试着弄坏它：添加空任务、疯狂切换、在复选框聚焦时删除、编辑到一半刷新。成品应用的定义，就是能扛住自己用户的折腾。

## 常见错误

**1. 直接改 DOM 而不改状态。** 手动切换复选框的类能奏效一次，随后就与数组——以及计数器——各奔东西。

```js
// 错误：DOM 与状态渐行渐远
checkbox.closest('li').classList.toggle('done');

// 正确：改状态，再从状态重渲染
task.done = checkbox.checked;
render();
```

**2. 用 innerHTML 拼用户输入的文字。** 一条名为 `<img src=x>`（再带个 `onerror` 属性）的任务就成了可执行的标记。用节点构建，输入永远是惰性文本。

```js
// 错误：任务文字被插值进标记
item.innerHTML = `<span>${task.text}</span>`;

// 正确：textContent 只能是文本
const span = document.createElement('span');
span.textContent = task.text;
```

**3. 表单忘了 preventDefault。** 提交导致页面重载，刚添加的任务凭空消失——看起来活像一个持久化 bug。

```js
// 错误：浏览器的默认提交行为赢了
form.addEventListener('submit', () => {
  addTask(input.value);
});

// 正确：先拦下导航，再处理数据
form.addEventListener('submit', (event) => {
  event.preventDefault();
  addTask(input.value);
});
```

**4. 有些变更保存，有些不保存。** 添加会保存，切换却不会——一次刷新就让任务起死回生。让每次变更都流经同一条以 `render()` 和 `save()` 收尾的路径。

**5. 无条件信任存储里取出的东西。** 上周的格式、写了一半的字符串、本该是数组的对象：不加防护的 `JSON.parse` 会在用户还没动手之前就让应用在启动时崩溃。

```js
// 错误：一个坏字节让应用开机即坏
tasks = JSON.parse(localStorage.getItem(KEY));

// 正确：try/catch 里解析、检查结构、默认空列表
tasks = loadTasks(); // 任何可疑情况都返回 []
```

**6. 把监听器写进 render() 里。** 每次重建列表再逐项绑定监听器，监听器层层叠加。监听一次、绑在容器上、用委托。

```js
// 错误：每次渲染都给每项再加一个监听器
tasks.forEach(() => li.addEventListener('click', handleDelete));

// 正确：一个监听器活过每一次渲染
list.addEventListener('click', handleClick); // 只在初始化时调用一次
```

## 进阶扩展（如果提前完成）

上面的练习是合格线。如果你还有富余时间，下面每一项都是真实的下一步功能——也是你已经掌握的某个模式的小型排练：

- **筛选**——列表上方放三个按钮（"全部""进行中""已完成"）。把当前筛选项存进一个变量，让 `render()` 决定显示哪些任务。注意状态模型悄悄多了一个字段。
- **就地编辑**——"重命名"按钮把文本替换成一个 `<input>`，在 `Enter` 或失焦时提交。你需要再加一个委托监听器，以及一次会触发重渲染的 `tasks` 更新。
- **更真实的计数**——加一个"清除已完成"操作，并为每个任务记录时间戳，用第 20 课的 `Intl.DateTimeFormat` 格式化显示。
- **拖拽排序**——最难的一个。查一下 `draggable`、`dragstart` 和 `dragover`；重排序本质上是用 `splice` 之类的操作改变数组，然后重新渲染。

最多选一个。你正在练习的纪律——先模型、再渲染、后事件——比功能清单更重要。

## 小结

- 一个应用，所有分层：HTML 结构、CSS 状态、JS 数据、DOM 事件、存储——每样都有自己的归属。
- 普通对象组成的数组就是应用本身；一个 `render()` 从它盖印屏幕，每次变更都走同一条 `变更、渲染、保存` 的路径。
- 表单 `submit` 加 `preventDefault` 负责添加；列表容器上委托的 `change` 与 `click` 监听器为所有任务——现有的和将来的——处理切换与删除。
- 持久化复用那套有防护的模式：`try/catch` 里 stringify 配内存回退，防御式 parse 加结构检查，默认为空。
- "可交付"意味着有标注、键盘友好、焦点得当，并且不惧刷新、存储故障和空看板——这正是你在全课程中反复达标的标准。

你已抵达轨道的终点。从这里出发：继续打磨这块看板（筛选、编辑、拖拽排序），或者带着这些模式走向框架——在那里，state、render 与单向数据流都会像老朋友一样迎你。
